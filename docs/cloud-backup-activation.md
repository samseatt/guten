The first cloud archive is `guten_20260919T004429Z_h0dzv3pg`. The backup role dumped Guten through verified TLS; age encrypted the stream without a plaintext dump on the database host. Its manifest and ciphertext were downloaded over SSH and restored into a disposable TLS-enabled PostgreSQL cluster on the Mac. All content/schema fingerprints matched the cloud baseline: 19 tables, 17 sequences, 125 columns and 32 indexes, including constraint definitions. The disposable cluster and volume were removed. Existing local/native and rehearsal services were not modified.

The local recovery identity is `.cloud-database/offline/backup-identity`, mode 0600. It was generated on the Mac; only its public recipient was sent to the database server. **Add this new identity to protected independent archives now.** The manual configuration archive made before this step does not contain it. Losing every copy makes these encrypted archives unrecoverable. Neither the private identity nor the CA private key belongs on the cloud server or in Git.

Local result: `.cloud-provision/encrypted-recovery.json`. Downloaded ciphertext: `.cloud-database/recovery-check/archive/`. This is a successful SSH-download recovery, not yet proof of S3 upload/download or scheduled execution.

## Admin setup procedure (completed)

GutenAudit is intentionally unable to create IAM identities or access keys. Use Chrome's Admin session and AWS CloudShell. The prepared file `.cloud-provision/setup-backup-access.py` was generated by:

```bash
python3 scripts/prepare_backup_access.py \
  --public-key .cloud-provision/guten-cloud.pub \
  --output .cloud-provision/setup-backup-access.py
```

Upload the generated Python file using CloudShell Actions > Upload file. Then run:

```bash
python3 ~/setup-backup-access.py
```

It verifies the account/Admin identity, refuses an existing uploader user, and checks the existing bucket's public-access block, versioning and SSE-S3 encryption. It creates `guten-backup-uploader` with no console password and a policy allowing PutObject, AbortMultipartUpload and ListMultipartUploadParts only under `guten-backups-983732020946-us-east-1/guten/database/`, over HTTPS. It grants no object read/delete, bucket administration or other AWS permissions. This is a long-lived machine access key; review and rotate it deliberately. Never install the personal Admin or GutenAudit session on the host.

A separate named inline policy, `GutenBackupRecovery`, gives GutenAudit read access to this bucket's configuration, listing restricted to that prefix, and encrypted-object reads for recovery verification. It grants no mutations. This intentionally extends the audit role to read Guten backup ciphertext, not unrelated bucket contents.

The new machine credential is immediately RSA-OAEP/SHA-256 encrypted with the existing Guten SSH public key and saved as `~/guten-backup-credentials.enc`. No plaintext credential is printed or written by the script. Download that encrypted file using CloudShell Actions > Download file, leaving it in the Mac Downloads folder. Do not paste credentials in chat. If the script fails after creating the IAM user, inspect and repair that same user/key; do not create extra identities. A rerun deliberately refuses an existing user.

The generated script was tested with a fake AWS CLI for wrong-account, existing-user and public-bucket refusals, minimum permission scope, encrypted credential round-trip, file permissions and rerun refusal. It was subsequently applied by the user in Admin CloudShell; see the live activation result below.

## Subsequent activation work

After the encrypted file is downloaded, `scripts/decrypt_backup_credentials.py` can decrypt it locally into a new mode-0600 file using the Guten private key. Transfer only the upload credential to `/etc/guten/secrets/backup_aws` on the database host (root-owned, 0600). Install the existing upload Compose override. Keep the recipient on the server and private recovery identity on the Mac.

Then, in order:

1. Verify live bucket policy/encryption/versioning through the scoped audit role.
2. Make a manual backup with S3 upload. Check that both ciphertext and manifest exist and that the upload-only identity cannot read/delete archives.
3. Download those exact objects using GutenAudit and repeat independent recovery with `scripts/verify_encrypted_backup.py`.
4. Run the systemd backup service manually and inspect its result; then enable the timer. Its schedule is 03:00 UTC plus up to 15 minutes jitter. Verify failed jobs surface clearly.
5. Choose external failure/missed-backup notification and conservative retention before unattended production cutover. Current tools perform no automatic deletion; storage is not unlimited and requires monitoring.

At the initial recovery checkpoint the timer was not enabled and upload credentials were pending. The activation below supersedes that state; external alerts and retention remain pending.

The recovery verifier takes `--archive`, `--identity`, `--expected` (cloud fingerprint JSON), and `--report`. It publishes no host ports, uses a uniquely named temporary PostgreSQL volume and removes it after verification. Its fixed private test subnet must not overlap an existing Docker network; Docker rejects overlap. The private recovery identity is mounted only in a local disposable client container. Plaintext recovery data exists in that client's `/tmp` tmpfs during restore.

No new paid AWS service is introduced here; archives will consume S3 storage and requests in the existing bucket. The initial archive is small; measure actual sizes before setting retention. There is no hard spending cap.

References: [S3 multipart permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html), [S3 operation permissions](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-policy-actions.html).


## Live S3 activation — September 18, 2026 local time

The encrypted credential handoff was decrypted only on the Mac. The uploader credential is installed root-owned mode 0600 at `/etc/guten/secrets/backup_aws` on the database host, mounted only into the backup container. The personal Admin/audit session and private age identity were not installed there. A protected local copy is in `.cloud-database/runtime/backup_aws`; refresh the independent configuration archive to include it.

Live audit API checks confirmed bucket versioning Enabled, all four public-access blocks enabled, SSE-S3 AES256 encryption, a bucket-policy deny for non-HTTPS access, and the existing seven-day incomplete-multipart cleanup. Completed archives are not expired.

Archive `guten_20260919T010852Z_0ntogrfw` was uploaded successfully. Its ciphertext is 632,351 bytes and manifest 260 bytes. GutenAudit downloaded both directly from S3. The independent Mac restore matched every cloud fingerprint category; the disposable recovery cluster/volume was removed. Proof is `.cloud-provision/s3-encrypted-recovery.json`. This verifies actual S3 recovery, beyond the earlier SSH-download test.

`scripts/test_backup_upload_permissions.py` verified the runtime identity is exactly `guten-backup-uploader` and received AccessDenied for reading an existing encrypted archive, listing the backup prefix, and deleting a random nonexistent object key. No existing archive was targeted for deletion. GutenAudit cannot inspect the IAM user's inline policy with its current permissions; the effective negative tests provide the live boundary evidence instead.

The actual `guten-backup.service` ran successfully and uploaded a second archive, `guten_20260919T011052Z_oz1n2yuq`, then passed its certificate-expiry check. An isolated transient service attempted upload outside the allowed prefix: AWS denied it, the process failed, and systemd recorded the failure in its journal. Its local encrypted archive remains available without an UPLOADED receipt; no remote object was written by that negative test.

`guten-backup.timer` is enabled. Daily target: **03:00 UTC plus 0–15 minutes jitter**. In Edmonton this is 9:00–9:15 p.m. during daylight saving time and 8:00–8:15 p.m. in winter. `Persistent=true` catches up a missed scheduled run after downtime. The first manual systemd run is verified; normal timed execution and full-host reboot catch-up have not yet been separately observed.

Repeatable installation is `deploy/database/activate-backups.sh`, run as root with its sibling `systemd/` folder after successful upload/download/restore validation. It checks credential ownership, validates the units, runs a real backup, then enables the timer. It does not grant IAM permissions or transfer private credentials.

Operational checks on the database host:

```bash
sudo systemctl list-timers guten-backup.timer --no-pager
sudo systemctl show guten-backup.service -p Result -p ExecMainStatus
sudo journalctl -u guten-backup.service -n 40 --no-pager
# Manual run (also uses the job lock):
sudo systemctl start guten-backup.service
```

Successful oneshot services return to `inactive`; check `Result=success` and `ExecMainStatus=0`, not whether they stay running. Disabling the timer stops scheduling; stopping the database host can prevent backups while Lightsail instance charges continue.

**Remaining before unattended production:** external failed/missed-run and disk-space notifications, deliberate local/S3 retention, and periodic independent recovery rehearsals. There is no email/push alarm and no automatic deletion yet. The operating-system journal is local evidence, not an off-host alarm. Keep monitoring it while those features are pending. At the current small archive size, retaining a few test copies is inexpensive, but future data growth must still be monitored.

Evidence logs: `.cloud-provision/backup-bucket-verification.json`, `backup-permission-tests.log`, `backup-systemd-first-run.log`, `backup-failure-propagation.log`, and `backup-timer-status.log`. No additional AWS infrastructure was created in this activation step; it uses the existing bucket and IAM identity.
